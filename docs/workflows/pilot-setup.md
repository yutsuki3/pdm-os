# パイロット開始前のシステム準備要件

## このドキュメントの位置づけ

[pilot-core-flow.md](pilot-core-flow.md) の実案件パイロットを開始するために、各正本システム側に用意しておく必要があるものを一覧化する。

内容は [source-of-truth.md](../architecture/source-of-truth.md) で確定した正本マッピングから逆算したものであり、ここで新しい業務ルールを決めるものではない。各項目には次を明記する。

- **必要な理由**: どの成果物・状態遷移がその設定に依存するか
- **最小要件**: これが無いとパイロットが進まないもの
- **【提案】**: PdM/PO未承認の具体案。採用・変更・却下はPdM/POが決める
- **対応TBD**: [tbd-register.md](../decisions/tbd-register.md) の該当ID

「最小要件」を満たさない項目が残っている場合、その工程はパイロットの対象外とするか、[run-validation-dry-run.md](../../prompts/run-validation-dry-run.md) の仮定として明示的に扱う。

## 1. Notion

正本となる情報が最も多い。要求原文・仕様書・承認記録・公開済みリリースノートの4種類を担う（[source-of-truth.md](../architecture/source-of-truth.md)）。

### 最小要件

| # | 用意するもの | 必要な理由 |
|---|---|---|
| N1 | 要求・要望の原文を置くページまたはDB | 要求原文の正本。`requested` の起点であり、要件・仕様書の出所参照先になる |
| N2 | 仕様書のページまたはDB | 現行仕様の正本。`spec_approved` はここへの反映を伴う |
| N3 | 承認記録用のプロパティ | 全5ゲートの承認記録先（[approval-policy.md](../architecture/approval-policy.md) で確定済み） |
| N4 | リリースノートのページまたはDB | 公開先・アーカイブ先。`released` の公開証跡 |

### 【提案】構成案

用途ごとに3つのDBを分け、承認記録は各DBのプロパティとして持つ。正本の境界がDB単位で明確になり、「どのページを見れば今の仕様が分かるか」が一意に決まる。

| DB | 1レコードの単位 | 主なプロパティ |
|---|---|---|
| 要求・要望 | 1件の要求原文 | 依頼元、依頼チャネル、記録日、影響度、緊急度、総合優先度、関連Work Item ID |
| 仕様書 | 1案件（Work Item）の仕様書 | Work Item ID、状態、承認者、承認日、要求・要望へのリレーション |
| リリースノート | 1バージョン | バージョン番号、リリース日、公開日、承認者、含まれるWork Item |

承認記録のプロパティは、ゲートごとに「承認者」「承認日」の組を持つ形を想定する（要件確定・仕様書承認・受領判断・QA依頼送付・リリース可否の5ゲート）。

要求・要望と仕様書を別DBにするのは、1つの要求が複数案件に分かれる場合と、複数の要求が1案件にまとまる場合の両方があるため。1案件1ページに統合すると、その対応関係を表現できなくなる。

### 対応TBD

- TBD-062: ページ・データベースの具体構成（この提案の採否）
- TBD-008: 意思決定ログ（なぜその仕様にしたか）の置き場所・フォーマット
- TBD-054: 状態遷移履歴を残すか、残す場合の記録先と最小項目

### 確認したいこと

- 既存のNotionに、要求・要望や仕様書のDBがすでに存在するか（存在する場合は新設せず既存に合わせる）
- 承認記録をプロパティで持つ場合、ゲートごとに列を分けてよいか

## 2. Jira

タスク状態とQA結果の正本（[source-of-truth.md](../architecture/source-of-truth.md)）。階層と課題タイプはすでに確定している。

### 確定済みの構造

- 1案件（Work Item）= 1ストーリー、その配下に複数タスク
- 課題タイプはJira標準（ストーリー / タスク）を使う
- デザインと実装の区別は課題タイプではなく**ラベル**（`design` / `implementation`）で表す

### 最小要件

| # | 用意するもの | 必要な理由 |
|---|---|---|
| J1 | 対象プロジェクト（プロジェクトキー） | タスク草稿の登録先。`jira_tasks_created` の前提 |
| J2 | ストーリーとタスクの課題タイプが使えること | 上記の階層を表現するため |
| J3 | `design` / `implementation` のラベル | デザイン／実装の区別。分解プロンプトが必ず付与する |
| J4 | QAチケットを起票できること | QA結果の正本。`qa_passed` / `qa_failed` の証跡 |

### 【提案】タスク作成時の必須項目

新規カスタムフィールドを作らず、Jira標準のフィールドだけで始める。パイロットで不足が分かってからフィールドを追加するほうが、使われないフィールドを作らずに済む。

| 項目 | 入れる内容 |
|---|---|
| 要約 | タスクのタイトル |
| 説明 | 概要、受け入れ条件、Work Item ID、仕様書（Notion）URL |
| ラベル | `design` または `implementation` |
| 親 | 案件のストーリー（タスクの場合） |

Work Item IDと仕様書URLを説明欄ではなく専用のカスタムフィールドにすると、Jira側から案件単位の検索・集計ができるようになる。パイロットで「Jiraから案件を横断的に見たい」場面が出てきた時点で追加を検討する。

### 対応TBD

- TBD-019: プロジェクトキーの具体値
- TBD-020: 必須カスタムフィールド（この提案の採否）
- TBD-021: ストーリー配下のタスクの分解粒度
- TBD-022: 見積りの単位・入力タイミング
- TBD-023: デザイン／実装タスク間の依存関係を表すリンク種別
- TBD-024: 配下タスクの進捗からストーリーの状態を導く規則
- TBD-067: QAチケットを階層のどこに置くか（ストーリー配下のタスクか、別課題か）

### 確認したいこと

- パイロットで使うプロジェクトキー
- ラベルの命名を `design` / `implementation` としてよいか（既存の命名規則がある場合はそちらを優先する）
- QAチケットを案件のストーリー配下に置くか、QA専用の別プロジェクト・別課題として扱うか

## 3. Slack

QA依頼の送付証跡の正本。`qa_requested` の完了条件は、送付投稿のパーマリンクが取得できること（[source-of-truth.md](../architecture/source-of-truth.md)）。

### 最小要件

| # | 用意するもの | 必要な理由 |
|---|---|---|
| S1 | QA依頼を送るチャンネル | 送付証跡の置き場所 |
| S2 | パーマリンクを取得・共有できること | `qa_requested` の遷移証跡として記録するため |

### 【提案】投稿の運用

1案件1投稿を親メッセージとし、以降のやり取りはそのスレッドに集約する。親メッセージのパーマリンクが案件のQA依頼を一意に指すため、証跡が1つに定まる。

親メッセージに含める最小項目:

- Work Item ID と案件名
- 仕様書（Notion）URL
- QAチケット（Jira）の課題キー
- 検証対象範囲・対象外
- 受領レポートへの参照

QAチケットのキーを投稿に書き、QAチケット側には投稿のパーマリンクを貼る。送付証跡（Slack）と結果（Jira）で正本が分かれているため、この相互リンクが無いと片方からもう片方を辿れない（TBD-065）。

### 対応TBD

- TBD-032 / TBD-051: 送付先チャンネル・投稿フォーマット
- TBD-065: SlackのQA依頼投稿とJiraのQAチケットの相互リンク方法（この提案の採否）

### 確認したいこと

- QA依頼に使うチャンネル（既存のQAチャンネルがあるか、新設するか）
- 1案件1スレッドの運用でよいか

## 4. Google Drive

受領原本の置き場所。デザインの正式成果物はFigma、実装事実はGitHubに確定しているため、Driveが担うのはそれ以外の受領物（提案書、Google Docsの成果物、納品ファイル等）になる。

### 最小要件

| # | 用意するもの | 必要な理由 |
|---|---|---|
| D1 | 受領原本を置くフォルダ | `delivered` → `acceptance_review` で突き合わせる対象 |
| D2 | どのファイルが受領原本かを判別できる規則 | 作業中ファイルと受領原本の区別 |

### 【提案】フォルダ構成

案件ごとにフォルダを作り、フォルダ名に Work Item ID を含める。受領原本はそのフォルダ直下に置き、作業中のファイルはサブフォルダに分ける。ファイル名の命名規則を新たに定めなくても、置き場所だけで受領原本を判別できる。

### 対応TBD

- TBD-028: 受領原本の特定方法（この提案の採否）
- TBD-026: 受領判断で参照するリポジトリ・フォルダの範囲

### 確認したいこと

- 既存のDriveに案件フォルダの構成・命名規則があるか
- そもそもパイロット対象案件でDriveの受領原本が発生するか（発生しない場合、初回パイロットではDriveを対象外にできる）

## 5. Figma

ワイヤーフローの正式成果物（[templates/wireflow.md](../../templates/wireflow.md)）。リポジトリ側のワイヤーフロー草稿は、画面ID・遷移・分岐条件を構造化して参照可能にするためのものであり、ビジュアルは持たない。

### 最小要件

| # | 用意するもの | 必要な理由 |
|---|---|---|
| F1 | 案件のFigmaファイル | ワイヤーフローの正式成果物 |
| F2 | 画面とワイヤーフロー草稿の画面IDの対応 | Jiraタスクの受け入れ条件が画面ID（`S2` 等）を根拠として参照するため |

### 【提案】画面IDの対応づけ

Figma側のフレーム名の先頭に、ワイヤーフロー草稿の画面IDを付ける（例: `S2 ...`）。Jiraタスクの受け入れ条件が `wireflow` / `S2` の形で根拠を参照するため、Figmaを見る側がその画面をすぐ特定できる必要がある。

### 対応TBD

- TBD-064: Figmaファイルの命名規則・格納場所
- TBD-030: Figma更新時にワイヤーフロー草稿を追随させる責任者・タイミング

### 確認したいこと

- パイロット対象案件でワイヤーフローが必要か（不要なら初回は対象外にできる）
- フレーム名に画面IDを付ける運用がデザイナー側の運用と衝突しないか

## 初回パイロットで最低限必要なもの

[pilot-core-flow.md](pilot-core-flow.md) の初回パイロットは要求・要望からJiraタスク草稿までが対象で、QA・リリース工程は含まない。したがって初回に必須なのは次の5つに絞られる。

1. **N1** 要求・要望の原文を辿れるNotionページ（またはPdM/POが原文を提示できること）
2. **N2** 仕様書の置き場所（承認後に人間が手動反映するため）
3. **J1** Jiraのプロジェクトキー
4. **J2 / J3** ストーリー・タスクの課題タイプと `design` / `implementation` ラベル
5. 検索を許可する正本システムと範囲の明示

Slack・QAチケット・リリースノートは初回パイロットの範囲外のため、この時点では未整備でも開始できる。
